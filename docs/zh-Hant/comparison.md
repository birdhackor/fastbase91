# 方案比較

**先講結論：** 如果你要的是「單執行緒一次編碼最快」，用 `pybase91`。如果你要平行跑很多次編解碼、要跑在自由執行緒 Python 或 Windows 上、要內嵌一個 `no_std` core，或要拒絕格式錯誤的輸入，就用 fastbase91。兩者產生的位元組完全相同、能互相解碼，所以你甚至可以同時用。

這裡每一個 basE91 實作都用標準演算法。fastbase91、`pybase91` 與本儲存庫的純 Python 參考實作逐位元組互通。

## pybase91 快在哪、為什麼

在單執行緒上，`pybase91`（`base91-rs` crate）的編碼比 fastbase91 快，這點我們不打算裝作沒這回事。原因很具體，也值得搞懂，因為它很容易被誤讀成「它用了 SIMD、我們沒有」。

`pybase91` 那條「可互通」的編碼器——也就是一般 `pybase91.encode()` 會呼叫的那條——是**手工調校過的純量（scalar）程式碼**：普通的、一次處理一個值的 Rust，但刻意排列成讓 LLVM 編譯器能編出很緊湊的機器碼。它單執行緒的優勢就來自這份手工調校。

它**也**帶了 SIMD 常式（一道指令處理很多位元組），但那實作的是**另一種、不相容**的編碼。標準的 `pybase91.encode()` 不會用到它們，而且它們的輸出不是你能交給別的函式庫的 basE91。所以公平的比較——大家實際會用的那條可互通路徑——是純量對純量，在那裡 `pybase91` 的手工調校在單執行緒上就是贏。

## fastbase91 被設計來贏的地方

- **並行處理。** 對 1,024 bytes 以上的呼叫，fastbase91 會用 `py.detach` 放掉 Python 的全域鎖（GIL），把工作交給 Rust，於是不同執行緒的呼叫能重疊執行。`pybase91` 整個呼叫期間都握著 GIL，所以多出來的執行緒只能等——它單執行緒的領先，換不成並行吞吐量。超過兩三條執行緒之後，fastbase91 的總吞吐量就會超車（見[效能測試](benchmarks.md)）。
- **對常見輸入零複製。** 當你傳入 `bytes`，fastbase91 會直接借用那塊 buffer（`PyBackedBytes`），而不是複製一份。這個借用之所以能在放掉 GIL 期間安全持有，正是因為 `bytes` 是不可變的——沒有東西能在呼叫進行到一半時改動它。（可寫入的 `bytearray` 或 `memoryview` 會先複製，因為它們**可能**被改。）
- **decode 不再是弱點。** fastbase91 現在把寬鬆（lenient）與嚴格（strict）解碼拆成兩條路。拆開之後，讓預設的寬鬆路徑大幅提速——在目前的測量中，大致與 `pybase91` 的解碼打平。嚴格解碼會逐位元組對照字母表，因此要換回一些速度，換到的是「拒絕壞輸入」。
- **它能跑在別人跑不了的地方。** 自由執行緒與 Windows wheel；可重用的 `no_std` Rust core，可跑裸機；`#![forbid(unsafe_code)]`；串流編解碼；以及會拒絕非字母表位元組（而不是略過）的嚴格解碼。

## 各實作一覽

| 方案 | 優點 | 取捨 |
| --- | --- | --- |
| **fastbase91** | 並行（大型呼叫放掉 GIL）；自由執行緒與 Windows wheel；`bytes` 零複製；可重用的 `no_std` Rust core；`#![forbid(unsafe_code)]`；串流；嚴格解碼 | 單執行緒編碼比 pybase91 慢 |
| **pybase91** | 這裡最快的單執行緒編碼，來自手工調校的純量 Rust | 握著 GIL，並行沒有加成；受比較的 0.2.2 版只發 macOS/Linux、Python 3.11–3.13 的 wheel，沒有自由執行緒或 Windows wheel |
| **純 Python** | 沒有編譯相依；Python 跑到哪它就跑到哪 | 在這些測量中大約比 Rust 版慢 100 倍 |

## 其他 binary-to-text 編碼

如果你根本不綁定 basE91，取捨主要是「體積」對「格式被支援的廣度」：

| 編碼 | 約略體積膨脹 | 說明 |
| --- | ---: | --- |
| base64 | ~33% | 到處都支援；Python 標準庫內建 |
| base85 | ~25% | 比 base64 緊湊；Python 標準庫內建 |
| basE91 | ~23% | 三者中最緊湊；91 字元的字母表用了較多標點符號 |

這些是不同的格式，不是同一件事的不同實作——base64 的輸出不是 basE91 的輸出。當「更省體積」值得你多裝一個函式庫時，選 basE91；當「在標準庫裡、大家都看得懂」更重要時，選 base64／base85。
